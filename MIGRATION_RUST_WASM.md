# Архитектурное руководство спецификации Платформы (Universal Core + WASM + Tauri)

Данный документ представляет собой подробную спецификацию целевой модульной платформы **Next-Gen Core Platform**: высокопроизводительного, безопасного и универсального микроядра на Rust + Wasmtime + Axum + Tauri, в которое посредством изолированных WASM-плагинов может интегрироваться абсолютно любой функционал (мониторинг, автоматизация, IoT, телеметрия, медиасервисы, интеграции и бизнес-логика).

> [!IMPORTANT]
> **Смена парадигмы (Universal Microkernel Platform):**
> Система больше не является узкоспециализированной NMS (системой сетевого мониторинга). Ядро проектируется как **domain-agnostic рантайм** (универсальный хост плагинов), предоставляющий безопасную песочницу, шину событий, изолированное хранилище, диспетчер задач, авторизацию и микрофронтенд-оболочку. Сам мониторинг и любые другие предметные области — это всего лишь подключаемые наборы модулей (плагинов).

## 🏛️ Часть 1. Как работает платформа

### 1.1. Двойной режим работы (Dual-Mode Execution)
Приложение представляет собой **один бинарный файл**, который адаптирует свое поведение в зависимости от окружения и аргументов командной строки:

```
                                  ┌──────────────────────────┐
                                  │   Исполняемый файл nms   │
                                  └─────────────┬────────────┘
                                                │
                       ┌────────────────────────┴────────────────────────┐
                       ▼                                                 ▼
        [Запуск с аргументом --server]                    [Запуск без аргументов / GUI]
                       │                                                 │
      ┌────────────────┴────────────────┐               ┌────────────────┴────────────────┐
      │ Headless Daemon / Docker        │               │ Tauri Desktop App               │
      │ • Без графического окна         │               │ • Инициализирует WebView окно   │
      │ • Запускает Axum HTTP/WS 24/7   │               │ • Поднимает локальный бэкенд    │
      │ • Выполняет опрос сетей по cron │               │ • Рендерит Vue 3 UI в окне      │
      └─────────────────────────────────┘               └─────────────────────────────────┘
```

### 1.2. Структура плагинов, манифест (`manifest.yaml`) и жизненный цикл WASM-песочницы

#### А. Структура архива плагина (`.nms-plugin`) и бескомпромиссное хранение (Zero-Unpack)
Плагины хранятся в каталоге `modules/` **непосредственно в виде единых архивов** (`.nms-plugin` / `.zip`) без необходимости распаковки на диск сервера (для локальной разработки также поддерживается обычный распакованный каталог):

```
modules/                                # Каталог установленных плагинов NMS
├── ping-collector-1.2.0.nms-plugin     # Единый архив плагина ping-collector
├── astra-monitor-2.0.1.nms-plugin      # Единый архив плагина astra-monitor
└── alert-telegram-1.0.0.nms-plugin     # Единый архив плагина alert-telegram
```

**Внутренняя структура архива `.nms-plugin`:**
```
ping-collector-1.2.0.nms-plugin (zip)
├── manifest.yaml                       # Single source of truth: метаданные, маршруты, шина событий, RBAC и схемы
├── backend.wasm                        # Серверный WASM-модуль бизнес-логики (Wasmtime Component Model)
├── signature.bin                       # Цифровая Ed25519-подпись (манифест + backend.wasm, опционально для dev)
├── locales/                            # Словари локализации бэкенда (опционально, например ru.json, en.json)
└── frontend/                           # Статические артефакты фронтенда (опционально)
    ├── views/                          # Сырые Vue SFC компоненты (для Dev / Legacy In-Browser компиляции)
    ├── dist/                           # Предсобранный ESM-бандл (основной продакшн-стандарт, например ui.js)
    └── assets/                         # Иконки, стили и ресурсовые файлы
```

* **Zero-Unpack Runtime & AOT Cache в Rust Core**:
  1. `manifest.yaml` читается парсером напрямую из zip-потока в память.
  2. **Цифровая подпись пакета (`signature.bin`) и управление ключами**:
     - **Модель доверия**: Корневой публичный ключ официального вендора встроен непосредственно в бинарный файл ядра. Дополнительные доверенные публичные ключи организаций и разработчиков подключаются через каталог `config/trusted_keys/*.pub` или перечисляются в `config.toml` (`security.trusted_public_keys = [...]`).
     - **Верификация**: Перед инициализацией ядро проверяет валидность Ed25519-подписи файла `manifest.yaml` и байткода `backend.wasm`.
     - **Политика для неподписанных и dev-плагинов**: В продакшн-режиме (`security.allow_unsigned_plugins = false`) неподписанные плагины блокируются или требуют явного аппрува администратором через UI/CLI (`--force-unsigned`). В локальном режиме разработки (`nms --dev` или `allow_unsigned_plugins = true`) неподписанные плагины загружаются с предупреждением в системном логе.
  3. **AOT Precompiled Cache (Холодный старт без повторной компиляции)**: `backend.wasm` извлекается в буфер памяти `Vec<u8>`, после чего ядро вычисляет SHA-256 хэш байткода и проверяет наличие предкомпилированного бинарника в `cache/modules/{id}-{hash}.cwasm`. Если кэш валиден, модуль инстанциируется через `Component::deserialize` мгновенно (целевой SLA инстанцирования из кэша < 5 мс против сотен миллисекунд JIT-компиляции); если нет — выполняется Cranelift AOT-компиляция, сохранение в кэш (`component.serialize()`) и запуск.
  4. Файлы интерфейса отдаются веб-сервером Axum потоково напрямую из архива по прямому пути `/modules/{id}/*` (например, `/modules/ping-collector/dist/ui.js`) с использованием **In-Memory LRU/Bytes кэша**, заголовков `ETag` и `Cache-Control: public, max-age=31536000` (исключая повторный I/O оверхед при чтении zip).
  5. Пользовательские данные и персистентное состояние модуля сохраняются в `data/nms.db` (KV/Settings) или в изолированном каталоге данных `data/modules/{id}/`.

`manifest.yaml` является **единым декларативным контрактом** модуля. Он специфицирует:

1. **Идентификация и совместимость**:
   * `id`: Уникальный строковый идентификатор модуля (kebab-case, служит пространством имен для шины событий и API).
   * `name`, `version`, `description`: Отображаемые метаданные и SemVer-версия.
   * `type`: Категория модуля (`system` — системный, `feature` — прикладной, `driver` — опрос устройств).
   * `min_core_version`, `max_core_version`: Диапазон поддерживаемых версий ядра `nms-core`.
   * `enabled_by_default`: Статус автоактивации при первой установке.

2. **Граф зависимостей и топология**:
   * `deps`: Обязательные зависимости от других модулей (на их основе ядро строит топологический порядок загрузки).
   * `optional_deps`: Опциональные зависимости для мягкой деградации функционала при их отсутствии.
   * `parent`: Идентификатор родительского модуля (для иерархических субмодулей).

3. **Интерфейс шины событий (Event Bus Contracts)**:
   * `events.publishes`: Белый список топиков событий, которые модуль имеет право публиковать в `nms:core/events`. Первый сегмент топика обязан строго совпадать с `id` модуля (защита от спуфинга чужих событий).
   * `events.subscribes`: Список топиков системных событий или событий других модулей, на которые плагин регистрирует подписку.

4. **UI-декларации и Dashboard (Интеграция в Shell)**:
   * `routes`: Клиентские страницы (путь `path`, имя `name`, путь к компоненту `component` — поддерживает ESM `dist/ui.js`, Vue SFC `views/Page.vue` или опускается для Schema-Driven автогенерации, метаданные `meta`: `title`, `icon`, `group`, `requires_auth`, `permissions`).
   * `menu`: Позиционирование в меню навигации (`location: sidebar | footer`, `group`, пункты с `label`, `icon`, `path`).
   * `widgets`: Виджеты для сводной панели (Dashboard) с параметрами `id`, `title`, `component` (ESM/SFC), `size`, `refresh_interval`, `endpoint`, `stream_endpoint`, `view_permission`, `control_permission`.

5. **Безопасность и модель доступа (RBAC)**:
   * `permissions`: Список гранулярных разрешений (`id`, `name`, `category`, `description`), регистрируемых модулем в общей матрице прав ядра.

6. **Схема конфигурации и хуки**:
   * **`config_schema`**: JSON Schema (Draft-07/2020-12) настроек модуля. Ядро валидирует пользовательский ввод по этой схеме, а фронтенд-оболочка автоматически строит по ней форму настроек плагина.
   * **`hooks`**: Декларация жизненных хуков модуля (`install`, `uninstall`, `on_enable`, `on_disable`).
   * **`assets`**: Каталоги кэша (`cache_dirs`) и изолированного хранилища данных (`data_dirs`).

7. **Системные возможности песочницы и повышение прав (`capabilities`)**:
   * **`network`**: Запрос прямого сетевого доступа WASI (`allow_raw_sockets: bool`, `allowed_hosts: list[str]`). По умолчанию `false` (сеть доступна только через безопасный Host API `nms:core/net`).
   * **`filesystem`**: Запрос на проброс директорий хоста (`allow_host_dirs: [{path, mode: "read_only" | "read_write"}]`). По умолчанию `[]` (доступно только изолированное KV-хранилище ядра).
   * **`environment`**: Доступ к переменным окружения ОС (`allow_env_vars: list[str]`).

##### Пример полного `manifest.yaml` плагина:
```yaml
manifest_version: 1
id: "ping-collector"
name: "Ping Network Collector"
version: "1.2.0"
description: "Периодический ICMP-опрос сетевых узлов и метрики доступности"
type: "feature"
enabled_by_default: true

deps:
  - "network-topology"

  - "alert-telegram"

capabilities:
  network:
    allow_raw_sockets: false    # false = работаем безопасно через Host API nms:core/net
  filesystem:
    allow_host_dirs: []         # Доступ к ФС хоста не требуется
  environment:
    allow_env_vars: []

events:
  publishes:
    - "ping-collector.node_unreachable"
    - "ping-collector.latency_spike"

    - "network-topology.node_discovered"

routes:
  - path: "/monitoring/ping"

      title: "ICMP Мониторинг"

  location: "sidebar"
  group: "Мониторинг"

    - path: "/monitoring/ping"

      icon: "activity"

widgets:
  - id: "ping_summary_widget"

    size: "medium"
    refresh_interval: 30

permissions:
  - id: "ping.view"
    name: "Просмотр графиков Ping"
    category: "Monitoring"
  - id: "ping.manage"
    name: "Настройка узлов и интервалов"

config_schema:

  install: "init_schema"
  on_enable: "resume_collection"
  on_disable: "pause_collection"

  cache_dirs: ["cache/"]
  data_dirs: ["data/"]
```

#### Б. Сравнительный анализ манифестов: Python vs Rust + WASM (Архитектурное обоснование)

При переходе с Python на Rust + WASM манифест претерпевает концептуальную трансформацию: он перестает быть «инструкцией по динамическому импорту Python-кода в процесс» и становится **«декларативным контрактом песочницы (Sandbox & UI Contract)»**.

##### 1. Что и почему полностью УДАЛЕНО из манифеста (Python-Legacy):

* ❌ **Секция `entrypoints` (`factory`, `router`, `services`, `settings` формата `pkg.mod:attr`)**:
  * **Как было в Python**: Ядро использовало `importlib.import_module()`, искало строковый путь `backend.modules.ping:PingService` или `router: "backend.modules.ping.api:router"` и динамически монтировало FastAPI роутеры и инстанцировало классы в общем пространстве памяти.
  * **Почему не актуально в Rust + WASM**:
    1. **Компиляция вместо интерпретации**: В Rust нет среды исполнения `importlib` и динамического поиска символов по строковым путям Python-файлов.
    2. **WASM Component Model & WIT**: Весь бэкенд плагина упакован в бинарный `backend.wasm`. Все точки входа, хуки и типы строго специфицируются на этапе компиляции через интерфейсные файлы **WIT (WebAssembly Interface Types)** (контракт `nms:core/*`). Ядро связывает WASM-экспорты напрямую в бинарном рантайме Wasmtime.
    3. **HTTP/API роутинг через Host API / RPC**: Плагин не может «внедрить свой HTTP-роутер» напрямую в ядро Axum. Вместо этого плагин регистрирует RPC-методы через WIT-интерфейс или обменивается типизированными сообщениями через шину событий ядра, гарантируя изоляцию памяти и защиту от зависания HTTP-сервера.
* ❌ **Pydantic-ссылки `entrypoints.settings`**:
  * **Как было в Python**: Указывался класс настроек Python (наследник `BaseSettings`/`BaseModel`).
  * **Почему не актуально**: Конфигурация в WASM-архитектуре стала строго декларативной и кроссплатформенной. Схема настроек задается стандартной **JSON Schema** в поле `config_schema`. Rust-ядро валидирует настройки с помощью крейта `jsonschema`, а фронтенд Vue 3 автоматически строит по ней форму в UI без необходимости передавать классы языков программирования.
* ❌ **Формат `pkg.module:attribute` в хуках**:
  * **Как было в Python**: `hooks: { install: "backend.modules.ping.setup:install_hook" }`.
  * **Почему не актуально**: В WASM хук `install: "init_schema"` ссылается не на путь к файлу на диске, а на символическое имя функции, **экспортируемой WASM-бинарником** (`(export "init_schema" (func ...))`).

##### 2. Что ДОБАВЛЕНО специального для Rust + WASM:

* ⚡ **Секция `capabilities` (Изоляция песочницы Wasmtime)**:
  * В Python любой сторонний модуль имел неконтролируемый доступ к системным сокетам, файловой системе и переменным окружения сервера.
  * В Rust ядро Wasmtime создает строгий `Capability-Based Sandbox`. Плагин объявляет в `capabilities` только те привилегии, которые ему действительно нужны (например, доступ к определенным хостам в сети `allowed_hosts` или проброс папок `allow_host_dirs`). Все остальное блокируется на уровне ядра рантайма.
* ⚡ **Строгий контроль ABI-совместимости (`min_core_version` / `max_core_version`)**:
  * Гарантирует совместимость WIT-интерфейсов хоста и клиентского WASM-байткода.

##### 3. Сводная таблица полей манифеста:

| Секция / Поле манифеста | Статус в Python | Статус в Rust + WASM | Архитектурная роль в Rust Core |
| :--- | :--- | :--- | :--- |
| **`id`, `name`, `version`, `type`** | ✅ Использовалось | ✅ **Обязательно** | Идентификация, версионирование, неймспейсы шины событий. |
| **`deps`, `optional_deps`, `parent`** | ✅ Использовалось | ✅ **Обязательно** | Построение графа DAG и топологический порядок инициализации. |
| **`capabilities`** (`net`, `fs`, `env`) | ❌ Отсутствовало | ⚡ **Критично (Новое)** | Настройка изоляции песочницы Wasmtime (Security Sandbox). |
| **`entrypoints`** (`factory`, `router`, `services`) | ✅ Ключевая секция | ❌ **Удалено (Legacy)** | Заменено на бинарный `backend.wasm` + WIT-контракты. |
| **`events`** (`publishes`, `subscribes`) | ✅ Использовалось | ✅ **Обязательно** | Валидация прав на топики шины `tokio::sync::broadcast`. |
| **`routes`, `menu`, `widgets`** | ✅ Использовалось | ✅ **Обязательно** | Регистрация UI-компонентов в Vue 3 Shell оболочке. |
| **`permissions`** | ✅ Использовалось | ✅ **Обязательно** | Регистрация прав модуля в RBAC-матрице Rust-ядра. |
| **`config_schema`** | ✅ Использовалось | ✅ **Обязательно** | Декларативная JSON Schema для валидации и UI-генератора. |
| **`hooks`** | ✅ Python paths | 🔄 **Имена WASM-функций** | Вызов экспортируемых функций `backend.wasm`. |
| **`assets`** (`data_dirs`, `cache_dirs`) | ✅ Использовалось | ✅ **Обязательно** | Выделение изолированных директорий в хранилище хоста. |

#### В. Жизненный цикл ядра и WASM-песочницы
1. **Инициализация Ядра (Rust Core)**:
   * Запуск асинхронного рантайма `tokio`.
   * **Инициализация БД (`sqlx` SQLite / Postgres)**:
     - Для SQLite настраиваются параметры высокой конкурентности: `PRAGMA journal_mode = WAL;`, `PRAGMA busy_timeout = 5000;`, `PRAGMA synchronous = NORMAL;`, `PRAGMA foreign_keys = ON;`.
     - Архитектура пула соединений: выделенный **Single-Writer Connection Pool** (гарантирует отсутствие конфликтов `database is locked` при фоновой записи 24/7) и масштабируемый пул Read-Only соединений для параллельных запросов API.
   * **Инициализация Гибридной Шины Событий**:
     - **Telemetry & Live Ephemeral Bus (`tokio::sync::broadcast`)**: высокочастотный pub/sub (емкость канала 1024 сообщений) для отправки метрик, графиков и WebSocket-трансляций UI. При возникновении `RecvError::Lagged(n)` подписчик логирует отставание и запрашивает актуальный снимок состояния через Storage/RPC.
     - **Reliable Event Journal (SQLite WAL + MPSC с Backpressure)**: системный журнал событий для критичных оповещений, изменений конфигурации и аудита. Гарантирует персистентность (Zero Loss) и курсорное чтение пропущенных событий.
   * **Системные сервисы ядра**:
     - Встроенный Prometheus экспортер `/metrics` (агрегация метрик хоста и плагинов).
     - Встроенный TLS-терминатор (`rustls`) для безопасного standalone-развертывания без обязательного reverse proxy.
     - Аварийный режим `safe-mode` (`--safe-mode`): старт ядра без загрузки пользовательских плагинов для устранения сбоев конфигурации через UI/CLI.
     - Системный сервис интернационализации `nms:core/i18n`.
   * Инициализация движка `Wasmtime` с поддержкой `async_support` и `component_model` (WIT-контракты `nms:core/*`).

2. **Загрузка и Семантическая Валидация Плагинов (Discovery & Validation)**:
   * **Поиск**: Сканирование каталогов `/modules/*/` и чтение файлов `manifest.yaml` (из zip архивов или dev-каталогов).
   * **Валидация схемы**: Проверка структуры `manifest.yaml` (десериализация через `serde_yaml` в строго типизированную структуру `ModuleManifest`).
   * **Проверка совместимости**: Проверка условий `min_core_version` / `max_core_version` относительно текущей версии `nms-core`.
   * **Валидация безопасности событий**: Проверка `events.publishes` — все публикуемые топики обязаны начинаться с префикса `{module_id}.*`. Модуль блокируется при попытке перехватить чужой топик.
   * **Построение графа зависимостей (DAG)**: Разрешение связей `deps`, проверка отсутствия циклических зависимостей и вычисление порядка инициализации модулей.
   * **Регистрация RBAC, UI и i18n**: Регистрация `permissions`, `routes`, `menu`, `widgets` и словарей локалей `locales/*.json` в глобальном реестре ядра.

3. **Изоляция, Модель Конкурентности и Выполнение в Песочнице (Sandboxing & Concurrency Model)**:
   * `backend.wasm` компилируется Wasmtime (AOT/JIT) в нативный байткод.
   * **Модель Конкурентности Плагина (WASI 0.2 Non-Reentrancy Guard)**:
     - Экземпляр `wasmtime::Store` не является потокобезопасным и не допускает параллельных/реентерабельных вызовов.
     - **По умолчанию (Single-Instance Actor)**: Каждый плагин запускается как изолированный актор в выделенном таске Tokio с входящей очередью сообщений (`tokio::sync::mpsc Mailbox`). Вызовы `on-event`, `on-timer` и `handle-rpc` диспетчеризуются последовательно, гарантируя целостность внутреннего состояния плагина без mutex-блокировок.
     - **Stateless Worker Pool (для высоконагруженной телеметрии)**: Для модулей обработки данных без сохранения состояния (Stateless stream parsers) ядро поддерживает пул независимых инстансов (`ResourcePool<Instance>`) с round-robin распределением входящих пакетов.
   * **Лимиты памяти и ресурсов**: Для каждого инстанса задается ограничение линейной памяти через `ResourceLimiter` (по умолчанию 128 МБ).
   * **Защита от зависания и лимиты времени (Epoch Interruption + Host Timeouts)**:
     - **Гостевой код WASM**: Движок Wasmtime конфигурируется с `Config::epoch_interruption(true)`. Системный таймер инкрементирует эпоху, и при зацикливании гостевого кода Wasmtime прерывает выполнение по Epoch Deadline (например, 5–10 сек), генерируя контролируемый Trap.
     - **Host-вызовы ядра**: Поскольку Epoch Interruption контролирует только гостевые инструкции WASM, все асинхронные Host API (`nms:core/net`, `nms:core/storage`, `nms:core/rpc`) на стороне хоста строго оборачиваются в `tokio::time::timeout(PER_CALL_TIMEOUT, ...)`. При задержке внешнего I/O хост возвращает плагину типизированную ошибку (например, `timed_out`), исключая блокировку потоков рантайма.
   * При возникновении фатальной ошибки внутри WASM (Trap / Out of Memory / Timeout) ядро перехватывает сбой, изолирует инцидент, регистрирует ошибку в аудит-логе и выполняет контролируемый перезапуск модуля **без влияния на работу ядра и других модулей**.

4. **Связывание (Linking) и Маршрутизация Ассетов**:
   * Веб-сервер Axum динамически маршрутизирует файлы плагина по прямому пути `/modules/{id}/*`, считывая их напрямую из архива `modules/{id}.nms-plugin` (или локальной папки в dev-режиме) с поддержкой In-Memory кэширования, ETag и Gzip/Brotli компрессии.

#### А. Взаимодействие Модуля с Ядром (Host WIT API & Guest Exports)

1. **Imports плагина (предоставляются ядром)**:
   * **`nms:core/events`**: Публикация событий в общую шину (`publish-telemetry`, `publish-reliable`).
   * **`nms:core/storage`**: Изолированное Key-Value хранилище модуля (`get`, `set`, `delete` с авто-префиксом `module:{id}:`).
   * **`nms:core/logger`**: Системная трассировка логов (`log-trace`, `log-debug`, `log-info`, `log-warn`, `log-error`).
   * **`nms:core/notify`**: Отправка оповещений пользователям (`send-alert`).
   * **`nms:core/cron`**: Регистрация периодических фоновых задач (`schedule-interval`).
   * **`nms:core/rpc`**: Динамический межмодульный вызов других плагинов через брокер ядра (`call`).
   * **`nms:core/net`**: Системный сетевой модуль ядра (асинхронный ICMP Ping через нативный сокет хоста, асинхронный HTTP/HTTPS клиент с пулом соединений, TCP/UDP probe и датаграммы для SNMP/Syslog от имени ядра без необходимости повышенных прав у WASM-песочницы).
   * **`nms:core/i18n`**: Сервис интернационализации (перевод системных ключей и фраз плагина с подстановкой параметров `translate(key, params)`).

2. **Exports плагина (полный WIT-контракт гостя для доставки событий, таймеров и RPC)**:
   Поскольку в WASI 0.2 / Component Model инстанс `Store` нереентерабелен, доставка сообщений выполняется последовательно через акторный Mailbox гостя:
   * **`nms:core/lifecycle`**: Хуки жизненного цикла (`on-install`, `on-uninstall`, `on-enable`, `on-disable`).
   * **`nms:core/event-consumer`**: Доставка событий шины, на которые подписан плагин (`on-event(topic: string, payload: list<u8>) -> result<_, string>`).
   * **`nms:core/timer-consumer`**: Обработка периодических срабатываний таймеров и cron (`on-timer(timer-id: string) -> result<_, string>`).
   * **`nms:core/rpc-handler`**: Обработка входящих межмодульных RPC-запросов (`handle-rpc(method: string, params: list<u8>) -> result<list<u8>, string>`).

   *Спецификация WIT-мира модуля (`wit/nms-core.wit`):*
   ```wit
   package nms:core@2.0.0;

   world plugin {
       // Host API (импортируется плагином из ядра)
       import events;
       import storage;
       import logger;
       import notify;
       import cron;
       import rpc;
       import net;
       import i18n;

       // Guest API (экспортируется плагином для вызова ядром)
       export lifecycle;
       export event-consumer;
       export timer-consumer;
       export rpc-handler;
   }
   ```

#### Б. 3 Способа Межмодульного Взаимодействия (Module ↔ Module)

Для решения различных инженерных задач применяются **3 дополняющих друг друга механизма**:

1. **Способ 1: Гибридная асинхронная шина событий (Event Bus Pub/Sub — 80% задач)**:
   * **Разделение потоков доставки**:
     - **Телеметрия и эфемеренные события (`tokio::sync::broadcast`)**: высокочастотные тики опроса, метрики, промежуточные статусы. При отставании подписчика (`RecvError::Lagged`) плагин фиксирует событие и при необходимости синхронизирует срез через RPC/Storage.
     - **Гарантированные системные события (Event Journal)**: запись в журнал SQLite WAL с гарантией персистентности и доставкой через MPSC очередь с backpressure.
   * **Канонический формат Payload (`list<u8>`)**:
     - **Базовый стандарт (Default)**: **JSON (UTF-8 байты)** — используется для 90% событий (изменение состояния узлов, системные алерты, жизненный цикл, аудит). Гарантирует максимальную прозрачность, простоту отладки и прозрачный проброс на веб-фронтенд через WebSocket без промежуточного перекодирования.
     - **Высокопроизводительный бинарный режим**: **MessagePack (msgpack байты)** — применяется для высокочастотной телеметрии, сбора сырых метрик опрашиваемых узлов и передачи объемных бинарных срезов данных.
     - **Конвенция топиков**: Топики с суффиксом `.stream` или `.bin` (например, `ping-collector.metrics.stream`) несут MessagePack, стандартные топики — структурированный JSON.
   * **Механика**: Модуль-источник (например, `ping-collector`) вызывает `events.publish("ping-collector.node_unreachable", payload)`. Все подписанные модули (например, `telegram-notifier`, `audit-logger`, WebSocket фронтенда) получают сообщения через свой экспорт `event-consumer.on-event`.
   * **Связность**: Нулевая (Loose Coupling). Источник не знает о существовании подписчиков; отключение подписчиков не влияет на работу источника.

2. **Способ 2: Динамический Mediated RPC через ядро (`rpc.call`)**:
   * **Сценарий**: Сервисный синхронный запрос данных без жесткой привязки версий (например, плагин отчетов запрашивает статус устройства: `rpc.call("ping-collector", "get_status", ip_bytes)`).
   * **Механика**: Ядро валидирует права в `deps`, проверяет активность целевого плагина, маршрутизирует вызов с хостовым таймаутом и возвращает ответ.
   * **Связность**: Слабая динамическая. Контролируется ядром с таймаутами и логированием сбоев.

3. **Способ 3: Прямое связывание компонентов (Direct Canonical ABI Linking via `deps` DAG)**:
   * **Сценарий**: Высоконагруженные критичные к задержкам вызовы между специализированными компонентами (например, драйвер опрашивает анализатор потока).
   * **Механика и роль поля `deps`**:
     1. Модуль-потребитель явно указывает модуль-провайдер в поле `deps` своего `manifest.yaml` (например, `deps: ["network-topology"]`).
     2. Ядро при старте строит **направленный ациклический граф (DAG)** и выполняет топологическую сортировку (`topological sort`).
     3. Сначала инстанциируются модули-провайдеры (уровень 0), а их экспортируемые WIT-интерфейсы регистрируются в `wasmtime::component::Linker`.
     4. Затем инстанциируются зависимые модули (уровень 1+), чьи импорты Wasmtime связывает с инстансами провайдеров **напрямую через Canonical ABI** (прямой FFI-вызов с безопасным копированием между изолированными памятями через `cabi_realloc`, исключая промежуточную сериализацию в JSON и очереди брокера ядра).
     5. **Субмодули (`parent`)**: Субмодули поставляются непосредственно в составе родительского плагина (единый `.nms-plugin` пакет), инициализируются и выгружаются синхронно с родителем, связываясь напрямую без оверхеда.
     6. **Необязательные зависимости (`optional_deps`) и отключение на лету**: Для `optional_deps` ядро монтирует легковесный **Atomic Host Trampoline (хост-трамплин)**. Если опциональный модуль активен — трамплин мгновенно перенаправляет вызов целевому плагину. Если модуль выключен администратором на лету — слот атомарно возвращает типизированную ошибку `Err(NotAvailable)`, исключая сбой зависимого плагина.
     7. **Управление жизненным циклом обязательных `deps`**: При отключении или обновлении обязательного провайдера ядро по графу `deps` каскадно и безопасно приостанавливает/перезагружает зависимые модули.
   * **Связность**: Сильная типизированная на уровне интерфейса (субмиллисекундная задержка вызова без текстовой сериализации).

#### В. 2 Режима Взаимодействия Модуля с Внешним Миром (ОС и Сеть)

Для взаимодействия с сетевым окружением и операционной системой архитектура предоставляет **два взаимодополняющих режима**:

```
                       ┌──────────────────────────────────────────────┐
                       │          WASM-плагин (backend.wasm)          │
                       └──────────────────────┬───────────────────────┘
                                              │
                    ┌─────────────────────────┴─────────────────────────┐
                    ▼                                                   ▼
     [Режим 1: Через Ядро (Host WIT API)]              [Режим 2: Повышение прав (WASI)]
                    │                                                   │
  • Стандартный безопасный режим (95% модулей)        • Прямой доступ к ОС (5% системных плагинов)
  • Вызовы: `nms:core/net`, `nms:core/storage`        • Плагин использует `std::net`, `std::fs`
  • Песочница полностью изолирована от ОС             • Ядро пробрасывает нативные сокеты/папки
  • Ядро само выполняет системные вызовы              • Требует прав `capabilities` в манифесте
```

1. **Режим 1: Через Хост API Ядра (Host WIT API — Стандартный Sandbox)**:
   * **Применение**: 95% модулей (мониторинг, отчеты, Telegram/Webhook оповещения, интеграции).
   * **Механика**: Модуль не имеет прямого доступа к сокетам и файлам ОС. Любые системные действия выполняются через интерфейс ядра `nms:core/net` (`ping`, `http-fetch`, `socket-probe`).
   * **Преимущества**: Абсолютная безопасность, отсутствие необходимости в root/`CAP_NET_RAW` правах, полный аудит запросов ядром и 100% кроссплатформенность.

2. **Режим 2: Через Повышение Прав (Direct WASI Capabilities — Прямой WASI 0.2 Sockets/FS/Env)**:
   * **Применение**: Модули со сложными протоколами поверх стандартных TCP/UDP или со сторонними Rust/C библиотеками, требующими стандартной библиотеки.
   * **Механика**: Модуль запрашивает права в секции `capabilities` файла `manifest.yaml` (`allow_network: bool`, `allowed_hosts: list[str]`, `allow_host_dirs`, `allow_env_vars`). После валидации цифровой подписи ядро конфигурирует `WasiCtxBuilder` в Wasmtime, пробрасывая стандартные сокеты WASI 0.2 (`wasi:sockets` TCP/UDP) и директории диска (`preopened_dir`).
   * **Важное разграничение**: Стандарт `wasi:sockets` поддерживает **только TCP и UDP**. Любые низкоуровневые Raw Sockets (AF_PACKET, SOCK_RAW, ICMP Ping, BPF/pcap сниффинг) **не входят в WASI** и всегда выполняются строго через нативный **Host API ядра (`nms:core/net`)** от имени Rust-хоста с правами ядра.
   * **Преимущества**: Возможность использовать стандартные библиотеки языка (`std::net::TcpStream`, `std::net::UdpSocket`, `std::fs::File`) без адаптации под кастомные API.

### 1.5. Локализация (i18n), системные логи и комментирование кода

* **Архитектура интернационализации (i18n) ядра и плагинов**:
  1. **Паритет с архитектурой Python (`backend/core/i18n.py`)**: Ядро содержит системный модуль локализации `nms:core/i18n` и базовые системные словари переводов (`locales/ru.json`, `locales/en.json`).
  2. **Поставка словарей плагинами**: Плагин может включать в свой архив каталог `locales/*.json`. При загрузке манифеста ядро регистрирует фразы плагина в общем реестре i18n с префиксом модуля (`module_id.key`).
  3. **WIT API для бэкенда плагинов**: Плагины могут запрашивать перевод системных сообщений, алертов и ошибок через хост-интерфейс `nms:core/i18n::translate(key: string, args: list<tuple<string, string>>) -> string`.
  4. **Клиентский i18n**: Фронтенд-оболочка (Shell) агрегирует словари ядра и активных плагинов, обеспечивая реактивное переключение языка интерфейса без перезагрузки страницы.
* **Англоязычный вывод системных логов**: В системные логи и журналы трассировки (ядро, WASM-песочница, stdout/stderr, `tracing`) весь текст сообщений выводится строго на английском языке для удобства автоматизированного парсинга и агрегации (Prometheus/Loki/Syslog).
* **Обязательное комментирование кода**: Весь исходный код (ядро Rust, WASM-модули, Web Components на Vue/JS, конфигурационные файлы) должен быть подробно прокомментирован. Все комментарии в коде пишутся строго на русском языке.

### 1.6. Унификация сетевого слоя (Tauri IPC vs Axum HTTP/WS)

Для предотвращения дублирования кода сетевых клиентов на фронтенде устанавливается **принцип единого транспорта (Unified Transport Protocol)**:

```
                               ┌──────────────────────────────────────────────┐
                               │       FRONTEND (Vue 3 / Web Components)      │
                               │  Использует единый REST / WebSocket Client    │
                               └──────────────────────┬───────────────────────┘
                                                      │
                                    HTTP / WebSocket (JSON / Binary)
                                                      │
                        ┌─────────────────────────────┴─────────────────────────────┐
                        ▼                                                           ▼
         [Режим Desktop (Tauri GUI)]                                 [Режим Server (Headless Daemon)]
                        │                                                           │
┌───────────────────────┴───────────────────────┐           ┌───────────────────────┴───────────────────────┐
│ Rust Core внутри Tauri процесса               │           │ Standalone Rust Server                        │
│ • Поднимает Axum на 127.0.0.1:{random_port}   │           │ • Поднимает Axum на 0.0.0.0:{config_port}     │
│ • Генерирует одноразовый Bearer token сессии  │           │ • Аутентифицирует пользователей через JWT     │
└───────────────────────────────────────────────┘           └───────────────────────────────────────────────┘
```

1. **Единый стек REST / WebSocket API**:
   - В режиме **Headless Daemon (`nms --server`)** Axum поднимет HTTP/WebSocket сервер на сконфигурированном внешнем или локальном порту (например, `0.0.0.0:8080`) с проверкой JWT в заголовках.
   - В режиме **Tauri Desktop App (`nms` без аргументов)** Rust-бэкенд поднимет локальный Axum HTTP/WS сервер на служебном loopback-интерфейсе `127.0.0.1:{random_port}` с генерацией криптографически стойкого одноразового сессионного токена (Session Bearer Token).
   - **Строгая безопасность Loopback**: Каждый HTTP-запрос от WebView к локальному бэкенду обязан содержать заголовок `Authorization: Bearer <session_token>`, а WebSocket-соединение валидирует токен при апгрейде (`Sec-WebSocket-Protocol: nms-auth, <token>` или query-параметр). Любые запросы от посторонних локальных процессов без токена отклоняются со статусом `401 Unauthorized`.
2. **Изоляция IPC `tauri::command`**: Использование нативного Tauri IPC ограничивается исключительно системными командами уровня ОС (управление окном приложения, сворачивание в трей, системные диалоги открытия файлов). Вся бизнес-логика и данные плагинов идут строго через Axum.
3. **Результат**: Фронтенд (Main Vue 3 Shell и динамические Web Components плагинов) использует **100% идентичный код сетевого клиента** в обоих режимах работы.

## 🔬 Часть 2. Обоснование Стека Технологий (Technology Rationale & Alternatives)

Ниже приведен детальный анализ выбора каждого элемента стека с аргументацией, почему были отвергнуты альтернативные варианты.

---

### 2.1. Язык Ядра: **Rust**

* **Почему выбран Rust**:
  1. **Безопасность памяти без GC (Garbage Collector)**: Отсутствие пауз сборщика мусора гарантирует стабильную предсказуемую задержку при опросе сетевых устройств 24/7.
  2. **Отсутствие GIL (Global Interpreter Lock)**: В отличие от Python, Rust использует нативные потоки ОС и асинхронный рантайм Tokio, эффективно масштабируя нагрузку на все ядра CPU.
  3. **Родная интеграция с Wasmtime**: Движок Wasmtime разрабатывается на Rust, что дает безопасный, строго типизированный FFI-слой без лишних накладных расходов.
  4. **Совместимость с Tauri**: Tauri написан на Rust, что позволяет использовать единый бэкенд для сервера и десктопа.
  5. **Целевые SLA эффективности**: Целевое потребление памяти ядра в простое: < 50 МБ RSS (против сотен мегабайт у интерпретируемых сред).

* **Почему отвергнуты альтернативы**:
  * ❌ **Python (Текущий стек)**: Наличие GIL, непредсказуемое потребление памяти при длительной работе с тяжелыми объектами, отсутствие аппаратной изоляции плагинов (любой сбой или `sys.exit()` в коде модуля завершает процесс всего сервера).
  * ❌ **Go**: Имеет Garbage Collector (GC), создающий недетерминированные паузы при интенсивном I/O. Менее удобная интеграция с Tauri и более тяжелый FFI при работе с Wasmtime C-API.
  * ❌ **C++**: Высокий риск уязвимостей безопасности памяти (Use-After-Free, Buffer Overflow, Data Races), отсутствие стандартной экосистемы пакетов уровня Cargo.

---

### 2.2. WASM Рантайм: **Wasmtime + WASI v2 (Component Model)**

* **Почему выбран Wasmtime**:
  1. **Официальный стандарт Bytecode Alliance**: Разрабатывается лидерами индустрии (Mozilla, Fastly, Red Hat, Intel).
  2. **Эталонная поддержка WASI v2 и Component Model**: Wasmtime — единственный рантайм с полноценной и самой зрелой поддержкой спецификации WASM Component Model (`.wit`), что позволяет генерировать строгие типы FFI для любых языков (Rust, Go, C++, Zig).
  3. **Безопасный Trap-handling**: В случае сбоя в WASM-модуле Wasmtime мгновенно изолирует ошибку и возвращает Rust `Result::Err`, не обрушивая процесс.

* **Почему отвергнуты альтернативы**:
  * ❌ **Wasmer**: Медленнее внедряет стандарты Component Model и WASI v2, сместился в сторону коммерческой экосистемы, имеет менее стабильные Rust-биндинги.
  * ❌ **WasmEdge**: Оптимизирован преимущественно под Edge/AI задачи и специфичные среды Linux, хуже документирован для работы с классическими серверными FFI в Rust.

---

### 2.3. Desktop Framework: **Tauri v2**

* **Почему выбран Tauri v2**:
  1. **Минимальное потребление памяти**: Десктопное приложение использует системный WebView ОС вместо встроенного Chromium.
  2. **Компактный размер дистрибутива**: Исполняемый файл занимает ~15-20 МБ (против 120+ МБ у Electron).
  3. **Прямое взаимодействие с Rust-ядром**: Бэкенд Tauri — это тот же Rust-код нашего сервера.

* **Почему отвергнуты альтернативы**:
  * ❌ **Electron**: Поставляет внутри себя полный браузер Chromium и Node.js, потребляя значительные системные ресурсы даже в фоновом режиме.
  * ❌ **Flutter Desktop**: Специфический язык Dart, сложности с динамической загрузкой Web Components плагинов, избыточный слой абстракции UI.

---

### 2.4. HTTP Framework & Async Runtime: **Axum + Tokio**

* **Почему выбрана связка Axum + Tokio**:
  1. **Единая экосистема**: Axum разрабатывается командой Tokio и является стандартом де-факто для высоконагруженных веб-сервисов на Rust.
  2. **Производительность**: Обрабатывает сотни тысяч запросов в секунду с минимальным накладными расходами (на базе `hyper`).
  3. **Удобство API**: Элегантная система макросов и экстракторов, аналогичная FastAPI, но со строгой типизацией на этапе компиляции.

* **Почему отвергнуты альтернативы**:
  * ❌ **Actix-web**: Использовал собственную экосистему акторов (раньше), менее прозрачная интеграция с Tokio, чуть более сложен в поддержке.
  * ❌ **Rocket**: Исторически отставал по поддержке async и современной экосистемы Tokio.

### 2.5. Frontend & Архитектура Плагинов: **Vue 3 + Vite + Гибридная Трехуровневая Модульная Система**

* **Основной стек ядра Frontend (Generic Shell)**:
  1. **Ядро UI (Оболочка)**: `Vue 3` (Composition API, `<script setup>`), `Vite`, `TypeScript`, `Pinia` (централизованное реактивное состояние), `Vue Router`.
  2. **Стилизация и темы**: `Tailwind CSS` с поддержкой динамических тем оформления (Dark/Light/High Contrast).
  3. **Базовые сервисы Shell**:
     * `WebSocket Client Manager`: Устойчивый к обрывам клиент для шины событий, системных нотификаций и реалтайм-данных от плагинов.
     * `Dashboard & Widget Grid`: Сетка виджетов и реестр динамических страниц, заполняемые модулями.
     * `i18n`: Интернационализация с поддержкой динамической подгрузки локалей из манифестов плагинов.
     * *Примечание*: Специфичные библиотеки визуализации (видеоплееры `mpegts.js`/`hls.js`, диаграммы `mermaid`, графики) инкапсулируются в соответствующих прикладных плагинах (Level 2/3), не утяжеляя базовый Shell ядра.

* **Трехуровневая гибридная система поставки UI плагинов**:
  1. **Уровень 1: Schema-Driven UI (Автогенерация форм настроек и конфигурации по JSON Schema)**
     * *Как работает*: Модуль поставляет только манифест `manifest.yaml` со схемой `config_schema` (поля, типы, дефолтные значения, ограничения `min`/`max` и валидаторы). Фронтенд-компонент `ModuleSettings.vue` автоматически генерирует типовую форму настроек без написания клиентского JS-кода.
     * *Применение*: Конфигурация и параметры 100% плагинов (настройки интервалов, адресов, токенов, переключателей).
  2. **Уровень 2: In-Browser Vue SFC (`.vue` на лету через `vue3-sfc-loader`) — [Dev / Legacy Mode]**
     * *Как работает*: Модуль поставляет сырой `.vue` файл в `/frontend/views/`. Компиляция шаблонов выполняется в браузере «на лету» через `vue3-sfc-loader`.
     * *Анализ рисков и безопасности CSP*:
       - Использование runtime-компилятора шаблонов требует добавления директивы `script-src 'unsafe-eval'` в Content Security Policy.
       - Это осознанное ослабление политики безопасности снижает устойчивость к XSS и нивелирует изоляцию стилей и DOM.
       - **Политика развертывания**: В production-режиме флаг `--disable-unsafe-sfc` активен по умолчанию со строгим CSP `script-src 'self'`. Уровень 2 предназначен исключительно для быстрой разработки и плавного транзита устаревших плагинов. Запланирован планомерный вывод из эксплуатации (Sunset).
     * *Ограничение режимов (Server vs Desktop)*:
       - **Server Web UI (`--server --allow-unsafe-sfc`)**: ✅ Доступен при явном включении администратором.
       - **Tauri Desktop App**: ❌ **Блокируется политикой безопасности**. В десктопном клиенте действует строгий CSP (`script-src 'self'`). При открытии такого плагина Shell выводит информационную плашку: *"Интерфейс модуля требует предсборки в ESM (dist/ui.js)"*.
  3. **Уровень 3: Предсобранный ESM / Web Components (`dist/ui.js` через Vite) — Основной Продакшн-стандарт (Dual-Mode Mainstream)**
     * *Как работает*: Разработчик плагина собирает интерфейс командой `npm run build` с полным контролем над TypeScript, Scoped CSS и библиотеками. Фронтенд загружает готовый артефакт через нативный браузерный `import('/modules/{id}/dist/ui.js')`.
     * *Совместимость*: ✅ **100% Dual-Mode** (одинаково и безопасно работает в Tauri Desktop и Server Web UI со строгим CSP без `unsafe-eval`).
     * *Применение*: Полнофункциональные интерактивные страницы, сложные аналитические дашборды, специализированные видеоплееры и графики.

* **Почему отвергнуты альтернативы**:
  * ❌ **React**: Потребовал бы полной и неоправданной переделки существующего фронтенда NMS с нуля (нарушение принципа YAGNI и reuse готовой кодовой базы).
  * ❌ **Pure Rust WASM UI (Leptos / Dioxus / Yew)**: Огромный оверхед и сложность интеграции со сторонними JS медиаплеерами (`mpegts.js`, `hls.js`), замедленный цикл разработки UI и проблемы с динамической загрузкой сторонних плагинов.
  * ❌ **IFrame**: Неприемлемый UX (сложности с адаптивностью, контекстными меню, всплывающими окнами, общим состоянием и сквозной аутентификацией).

### 2.6. База Данных: **SQLx (SQLite / PostgreSQL) & Repository Pattern**

* **Архитектурная стратегия поддержки двух СУБД и надежность SQLite**:
  1. **Изоляция диалектов через Repository Pattern**: Доступ к данным инкапсулируется за трейтами хранилища (например, `trait DeviceRepository: Send + Sync`). Бизнес-логика ядра работает с абстракцией и не зависит от конкретной СУБД.
  2. **Решение проблемы конкурентности SQLite (`database is locked`)**:
     - **WAL-режим**: Все подключения автоматически выполняют `PRAGMA journal_mode = WAL;`, позволяя читателям не блокировать писателей, а писателям — читателей.
     - **Busy Timeout**: Установка `PRAGMA busy_timeout = 5000;` для автоматического ожидания освобождения блокировки.
     - **Синхронизация и целостность**: `PRAGMA synchronous = NORMAL;` и `PRAGMA foreign_keys = ON;`.
     - **Разделение пулов соединений (Single-Writer Pool)**: Для SQLite ядро инициализирует ровно **одно writer-соединение** (с очередью транзакций в Tokio) и масштабируемый пул read-only соединений. Это фундаментально предотвращает гонки блокировок при круглосуточной записи журналов событий и метрик.
  3. **Compile-time проверка и разделение Feature Flags**:
     - Поскольку макросы `sqlx::query!` привязываются к конкретному типу подключения и схеме, поддержка разделена через Cargo Features: `--features sqlite` (по умолчанию для Desktop/Standalone) и `--features postgres` (для Enterprise Server).
     - В CI/CD поддерживаются два раздельных оффлайн-кэша запросов: `.sqlx/sqlite` и `.sqlx/postgres`.
  4. **Динамические запросы через `sqlx::QueryBuilder`**: Для общих фильтраций и CRUD-операций используется `QueryBuilder`, автоматически генерирующий корректные плейсхолдеры (`?` для SQLite и `$1` для Postgres).
  5. **Асинхронность**: 100% неблокирующий I/O для Tokio-рантайма без спавна лишних OS-потоков.

* **Почему отвергнуты альтернативы**:
  * ❌ **Diesel**: Синхронный ORM (требует спавна отдельных блокирующих потоков), тяжелый DSL, затрудняющий кастомные SQL-оптимизации.
  * ❌ **SeaORM**: Дополнительный слой абстракции поверх SQLx, увеличивающий время компиляции и усложняющий низкоуровневый тюнинг.

### 2.7. Сбор системных журналов и Логов: **Кроссплатформенный Tracing + Multi-OS Log Providers**

* **Почему выбрана эта связка**:
  1. **Кроссплатформенность и абсолютная портативность**: Приложение может запускаться на любой ОС (Linux с systemd/OpenRC, Windows Server, macOS, Docker). Абстракция `LogProvider` на Rust адаптирует чтение логов под текущую систему:
     - **Linux (systemd)**: Нативная интеграция через сокет `systemd-journal`.
     - **Linux (без systemd) / Unix**: Чтение Syslog (UDP/Unix socket) и файлов журналов.
     - **Windows**: Интеграция с Windows Event Log (`winlog`) и файлами логов.
  2. **Единый асинхронный пайплайн трассировки**: Библиотека `tracing` обеспечивает эффективное логирование событий ядра и WASM-модулей независимо от платформы.
  3. **Стандарт языка логов (English-Only)**: Сообщения логов формируются исключительно на английском языке для удобства автоматизированного мониторинга, грепа и анализа.

---

### 2.8. Безопасность и Аутентификация: **Argon2id + Ed25519 JWT + Ring + TLS (rustls)**

* **Почему выбрана эта связка**:
  1. **Защита от перебора паролей**: Использование стандарта OWASP Argon2id для хэширования паролей пользователей.
  2. **Быстродействующая криптография**: Пакеты `ring` / `ed25519-dalek` выполняют криптографические операции проверки токенов и шифрования секретов без сторонних зависимостей OpenSSL.
  3. **Встроенный TLS-сервер (`rustls`)**: Ядро нативно поддерживает защищенные HTTPS/WSS соединения в standalone-режиме без необходимости обязательной настройки внешнего Nginx/Caddy.

---

### 2.9. Уведомления и Фоновые Задачи: **Tokio Cron Engine + Reqwest Async**

* **Почему выбрана эта связка**:
  1. **Нативная асинхронная рассылка**: Рассылка алертов в Telegram, Webhooks и E-mail выполняется параллельно без блокировки цикла опроса сетевых устройств.
  2. **Планировщик задач**: Замена тяжелого Python APScheduler на легкий асинхронный планировщик на базе `tokio-cron-scheduler`.

---

### 2.10. Системные Сервисы Ядра: **Сетевой Модуль (nms:core/net), Метрики и Safe-Mode**

* **Почему сетевые и системные операции вынесены в ядро**:
  1. **Изоляция и Безопасность WASM**: Стандартная песочница WebAssembly не имеет прямого доступа к сокетам ОС и сырым пакетам (Raw Sockets). Вынесение ICMP/Ping, HTTP и UDP в Host-сервис ядра избавляет от необходимости давать WASM-модулям системные привилегии уровня root/`CAP_NET_RAW`.
  2. **Высокая производительность (Tokio Socket Drivers & Connection Pooling)**: Асинхронные сокеты хоста на базе `socket2`, `tokio::net` и `reqwest` пула соединений выполняют параллельный опрос тысяч сетевых узлов и сбор потоков (SNMP, Syslog, RTSP, HTTP API) с минимальным оверхедом.
  3. **Кроссплатформенная абстракция сокетов**: Плагины вызывают унифицированный WIT-интерфейс `nms:core/net`, а ядро автоматически адаптирует системные вызовы под Linux (epoll, ping sockets), Windows (IOCP, IcmpSendEcho2) и macOS (kqueue).
  4. **Встроенный Prometheus Экспортер (`/metrics`)**: Ядро агрегирует счетчики запросов, длительность вызовов WASM-плагинов, использование памяти песочницами и системные метрики хоста.
  5. **Аварийный Safe-Mode (`--safe-mode`)**: При повреждении конфигурации или циклическом падении модулей ядро запускается с изолированным веб-интерфейсом восстановления, блокируя загрузку сторонних плагинов до устранения причин сбоя администратором.

     - **`docs/wiki/02-usage/` (Подробное руководство по использованию и эксплуатации системы)**:

       * **Основные тематические блоки раздела**:

     - **`docs/wiki/03-module-development/` (Подробное руководство по разработке модулей и плагинов)**:
       * Предназначено для разработчиков расширений (WASM/Rust), UI Web Components (Vue 3) и контрибьюторов ядра.
       * **Основные тематические блоки раздела**:
         1. **Окружение и стандарты разработки**: Настройка локальной среды (Rust toolchain, target `wasm32-wasip2` с использованием `cargo-component` для WASI 0.2 / Component Model (либо `wasm32-wasip1` + `wasi_snapshot_preview1.reactor.wasm` адаптер), Node.js/Vite, Tauri CLI), стандарты оформления кода, обязательное комментирование на русском языке, написание Unit/Integration тестов.
         2. **Архитектура плагинной системы**: Структура `.nms-plugin` ZIP-пакета, спецификация манифеста `manifest.yaml`, модель безопасности Wasmtime, запрашиваемые capabilities и лимиты ресурсов (CPU epoch interruption / fuel, memory limits).
         3. **Спецификации WIT-контрактов ядра (`nms:core/*`)**: Для каждого системного сервиса ядра (`events`, `storage`, `logger`, `notify`, `cron`, `net`, `rpc`, `i18n` и т.д.) создается отдельный файл `0X-{module-name}.md` (например, `01-events.md`, `02-storage.md`, `03-net.md`, `04-i18n.md`).

         4. **Практические руководства**: Жизненный цикл плагина `backend.wasm` (`lifecycle`, `on-event`, `on-timer`, `handle-rpc`), создание пользовательских интерфейсов на Vue 3 Custom Elements, работа с дизайн-токенами ядра, сборка и упаковка плагинов с помощью `nms-cli`.
