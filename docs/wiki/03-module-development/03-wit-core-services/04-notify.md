# 🔔 WIT Интерфейс `nms:core/notify` — Система Уведомлений и Алертов

## 1. Назначение и архитектурная роль в платформе

Интерфейс `nms:core/notify` является системным контрактом микроядра, через который гостевые WASM-модули и системные сервисы отправляют структурированные оповещения об инцидентах, сбоях оборудования, аномалиях метрик и событиях безопасности.

### Архитектурный поток доставки алертов:

```text
┌────────────────────────────────────────────────────────────────────────┐
│                        WASM Guest Plugin Sandbox                       │
│   notify::send_alert(Critical, "Сбой BGP", "Peer 10.0.0.1 недоступен") │
└───────────────────────────────────┬────────────────────────────────────┘
                                    │ WIT Host Trampoline (Wasmtime)
┌───────────────────────────────────▼────────────────────────────────────┐
│                       Rust Microkernel Host Core                       │
│                                                                        │
│  1. Валидация прав: проверка capabilities плагина                      │
│  2. Присвоение метаданных: UUID, timestamp (UTC), source (plugin_id)   │
│  3. Регистрация в Journal: Reliable Event (SQLite WAL `event_journal`) │
│  4. Broadcast в WebSocket: отправка клиентам на `/ws/events`           │
│  5. Диспетчеризация каналов оповещения (NotifyService):                 │
│     ├── Webhook (HTTP POST c HMAC подписью)                            │
│     ├── Telegram Bot API (асинхронная очередь)                         │
│     └── Email (SMTP / STARTTLS)                                        │
└────────────────────────────────────────────────────────────────────────┘
```

## 2. Полный код WIT спецификации (`nms-core.wit`)

```wit
package nms:core@2.0.0;

interface notify {
    /// Уровни критичности системных оповещений
    enum alert-severity {
        /// Информационное сообщение (не требует немедленных действий)
        info,
        /// Предупреждение о потенциальной проблеме или деградации сервиса
        warning,
        /// Критическая авария, требующая незамедлительного вмешательства
        critical,
    }

    /// Отправить системное оповещение администраторам
    /// 
    /// # Параметры:
    /// - `severity`: уровень важности оповещения (info, warning, critical)
    /// - `title`: краткий заголовок события (отображается в push-уведомлениях и теме письма)
    /// - `message`: подробный текст с контекстом ошибки или описанием инцидента
    ///
    /// # Возвращаемое значение:
    /// - `ok`: алерт успешно поставлен в очередь доставки
    /// - `err(string)`: описание ошибки валидации или сбоя очереди ядра
    send-alert: func(severity: alert-severity, title: string, message: string) -> result<_, string>;
}
```

## 3. Детальное описание типов данных и уровней критичности

| Уровень (`AlertSeverity`) | Назначение и критерии срабатывания | Поведение диспетчера ядра | Отображение в UI |
| :--- | :--- | :--- | :--- |
| **`Info`** | Плановые события, перезапуск модуля, обновление конфигурации, успешное восстановление связи. | Запись в `event_journal`, WebSocket broadcast на дашборд. Не отправляется в экстренные SMS/Telegram каналы. | Синий бейдж, автоматическое скрытие через 10 секунд. |
| **`Warning`** | Рост задержки выше порога, единичные потери пакетов, заполнение диска > 80%, приближение лимитов памяти. | Запись в `event_journal`, звуковой сигнал в веб-интерфейсе, опциональная отправка в Telegram/Slack. | Желтый бейдж, требует ручного квитирования (Acknowledge). |
| **`Critical`** | Полная потеря связи с узлом (Down), отказ дискового массива, аппаратная авария питания, сбой BGP/OSPF. | Немедленная гарантированная отправка во все настроенные каналы (Telegram, SMS, Webhook), непрерывный тревожный сигнал в UI. | Красный пульсирующий баннер, блокирующий экран оператора до квитирования. |

## 4. Полноценный практический пример на Rust (Гостевой код плагина)

Пример мониторинга сетевого устройства с валидацией порогов, защитой от флуда (Rate Limiting) и отправкой алертов через `nms:core/notify`:

```rust
// src/lib.rs (WASM Component)
#[allow(warnings)]
mod bindings;

use bindings::nms::core::logger::{self, LogLevel};
use bindings::nms::core::notify::{self, AlertSeverity};
use bindings::nms::core::storage;

/// Структура метрик устройства
struct DeviceMetrics {
    pub ip: String,
    pub packet_loss_percent: f32,
    pub rtt_ms: f64,
}

pub fn analyze_device_health(metrics: &DeviceMetrics) {
    // 1. Проверка на критическую потерю связи
    if metrics.packet_loss_percent >= 100.0 {
        let title = format!("Узел {} НЕДОСТУПЕН (Host Down)", metrics.ip);
        let message = format!(
            "Зафиксирована 100% потеря пакетов до узла {}. Задержка RTT: N/A. Проверьте питание и оптическую линию.",
            metrics.ip
        );

        logger::log(LogLevel::Error, &format!("Triggering CRITICAL alert for {}", metrics.ip));

        if let Err(e) = notify::send_alert(AlertSeverity::Critical, &title, &message) {
            logger::log(LogLevel::Error, &format!("Failed to dispatch alert: {}", e));
        }
        return;
    }

    // 2. Проверка на деградацию канала (Warning)
    if metrics.packet_loss_percent > 15.0 || metrics.rtt_ms > 250.0 {
        let title = format!("Деградация канала до узла {}", metrics.ip);
        let message = format!(
            "Обнаружены аномалии на узле {}: потери пакетов {:.1}%, задержка {:.2} мс.",
            metrics.ip, metrics.packet_loss_percent, metrics.rtt_ms
        );

        let _ = notify::send_alert(AlertSeverity::Warning, &title, &message);
    }
}
```

## 5. Обработка ошибок и гарантированная доставка

1. **Гарантия сохранности при сбое сети**: Если внешний сервис отправки (Telegram API / SMTP) временно недоступен, алерт не теряется: ядро сохраняет его в персистентной таблице `event_journal` (SQLite WAL) и выполняет повторные попытки отправки с экспоненциальной задержкой (Exponential Backoff).
2. **Изоляция от паники плагина**: Если гостевой модуль падает сразу после отправки алерта, само сообщение уже безопасно передано хосту и гарантированно доставляется операторам.
